## What it catches

the worktree pruner's durability test cannot be fooled by a hand-made `refs/remotes/pr/<N>` mirror: work held only by one is reported UNSAFE instead of being removed, while genuinely pushed/merged work is still removed and a live worker's worktree is still kept; and its exit-code contract is read off real runs — a deliberate keep with a reclaim is `0`, keeping at-risk work while reclaiming nothing at all (artefact reaps included: the summary line's `artefacts=` count is asserted, and a run whose ONLY reclaim is a reaped `web/node_modules` in a worktree kept for an at-risk reason is `0` — card `t_ef95e467`) is `3`, a failed removal / unreadable card / failed fetch is `1`, and an unknown argument is `2` having run nothing. Every failure branch has its own run behind it, including the two the contract gained with the exit codes: the CARD loop's and the STRAY loop's unresolvable HEAD (`1`, logged as a `FAIL`, never a silent keep) and the STRAY loop's refused removal (`1`, `failures=1`) — card `t_7360634f` measured all four green against one-armed mutants before they were pinned. Card `t_e7ac4bcd` added the vanished-pid arm: a pid the process scan listed that is already GONE by the time its cwd and `status` are read (both reads fail, and there is no `/proc/<pid>` left) is SKIPPED, not reported as a live pid with an unreadable cwd — with the pre-fix predicate reading the very same synthetic row as that cannot-judge as its CONTROL, so the assertion bites, and the fail-safe pinned alongside it (a pid whose directory IS still there stays the cannot-judge and exits 1). Card `t_e89e95c7` removed the last fixed sleep in front of a `match` assertion: the STRAY section's stand-in premise was STILL a fixed `sleep 0.6` in front of one (`#1486` had replaced only the card loop's), and its stand-in's own `sleep 40` lifetime was a deadline the run can outlive on a loaded host — the premise now asks the pruner's own predicate in a bounded loop (`wait_for_guard`), the stand-in is held until the suite kills it, and a new check requires it to still be ALIVE when the run finished, so the two reds an expired stand-in produces (`a worktree … SURVIVES` + the missing `KEEP … (worker process alive)`) cannot be read as a broken guard — that exact pair was reproduced by shrinking the old lifetime to 1s (`209 passed, 2 failed`, on the pre-change bytes). Card `t_1483975b` made a red READABLE from the outside: the failure message now shows the haystack's HEAD **and TAIL** (a head-only `cut -c1-600` printed the card loop and cut off the stray/artefact verdicts the assertion was asking about — measured on that card's own flake, whose log never said why the stray was kept), the three `wait_for_cwd` premises report WHICH way they failed (`pid N is GONE` vs `pid N is alive, its cwd reads …`, so "never scheduled" is distinguishable from "in the wrong directory" — anything but exactly `yes` is still a red), and a red copies the pruner's own logs outside the sandbox and prints the path, so the evidence outlives the `rm -rf $SB`. It also CLOSED the flake, once that diagnostic had named it: the cwd guard read a task in the middle of `do_exit()` — its memory already released, so `/proc/<pid>/cmdline` is EMPTY, while `exit_fs()` has taken the cwd link and `exit_notify()` has not yet made the state `Z` (a task blocked in `D` on the way out can sit there) — as "a live pid whose cwd could not be read", i.e. a cannot-judge that keeps a removable worktree AND fails the run. It is now SKIPPED like a zombie (no argv area ⇒ no memory ⇒ no cwd it could hold), while a refused read on a task that still HAS an argv area stays the cannot-judge, unchanged. Pinned by a synthetic fixture and the pre-fix control, and measured: the gate reddened twice in one session on trees that had not touched the pruner (pids 480446 and 487809, `212 passed, 1 failed` then `213 passed, 0 failed` on the same bytes), and the suite now reads `217 passed, 0 failed` — re-measured on the tree that carries BOTH this card's run-unique ids and #1547's pruner fix (`--only prunewt`, 2026-11-05: `217 passed, 0 failed`). Card `t_d243986f` made the fixture's ids RUN-UNIQUE, and that is a correctness property, not tidiness: several assertions here are about the WHOLE host, and the pruner asks "is anyone working in this worktree" with `has_process_matching "worktrees/$name "` — a LITERAL substring carrying the CARD ID — so two copies of this suite sharing an id namespace MEASURE EACH OTHER (a peer's own `git worktree add …/worktrees/t_00000003 <sha>` satisfies this run's guard for a worktree nothing local is holding).
